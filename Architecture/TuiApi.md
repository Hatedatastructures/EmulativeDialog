# C++ TUI API 合同

TUI 由项目使用 C++ 自行实现，不是第三方 TUI 框架的封装。本文件在开始编写渲染代码前定义预期行为。

## 参照实现与零差异门

“完美还原”必须能对照一个确定目标。开始 TUI 实现前，产品 owner 必须在 Research/TuiReferenceMatrix.yaml 中锁定 TypeScript 参照库的名称、版本/提交、公开 API 范围、终端假设和测试场景。未选择具体参照库时，TUI 实现不得标记 Ready，也不得用“风格接近”代替验收。

验收按该版本的全部批准公开 API 建立一对一条目：每个组件/属性/布局约束/事件/输入/样式/生命周期都映射到 C++ API、参数语义、可观察行为和对照用例。目标范围内的 API 映射覆盖率必须为 100%；未批准的缺项、占位实现和行为差异必须为零。某项确实不适用于原生 Windows TUI 时，须由产品 owner 通过 ChangeRequest 明确排除，并在矩阵中保留原因和影响。

视觉和交互对照以固定场景、终端能力矩阵和单元格帧/事件结果为准。相同输入、尺寸、主题和流式事件必须得到相同布局、焦点、选择和可观察输出；所有差异都要有说明和批准。外部字体栅格造成的像素差异不作为跨终端可控对象，但不得借此豁免布局、字素宽度、裁切、颜色语义、滚动或输入行为。

C++ 必须提供同等完整的组件、属性、状态、事件和生命周期 API。API 名称及参数意义尽可能与参照库对应；JSX 的 TypeScript 语法本身不能成为原生 C++ 语法，也不能以嵌入 JS runtime 解决，因为产品运行时约束为 C++。这一语法差异不允许缩减组件能力或行为。若用户要求字面相同的 JSX 源语法，必须先通过 ChangeRequest 重新决定运行时边界。

## TUI Epic 与能力切片

TUI 是长期 Epic，不是一个“小任务”。按稳定合同和不重叠写集逐步形成可合并 PR；不为每个控件制造空 PR，也不把整个 TUI 一次性塞进一个任务。典型切片包括：

1. Windows TerminalSession、VT/ConPTY 能力检测、输入/输出模式保存与恢复。
2. UTF-8 解码、字素簇、终端显示宽度和单元格文本模型。
3. 单元格缓冲、前后帧差异渲染、颜色/样式和安全转义。
4. 行列布局、约束、尺寸变化重排、裁切和滚动视口。
5. 组件树、状态绑定、焦点和事件分发的 C++ 公共 API。
6. 键盘、粘贴、鼠标、resize、取消和异常退出路径。
7. 参照 API 对照夹具、差异报告、性能与恢复门。
8. 聊天界面组合：会话列表、消息时间线、输入、流式回复和状态面板。

每个切片按 Architecture/ModuleMap.yaml 指派唯一 owner。跨切片公共类型先冻结合同；终端、布局、组件和输入不允许多 Agent 写同一文件。

## 必需行为

- 组件树具有明确且可预测的父子所有权。
- 支持类似 Flex 的行/列布局、最小/最大尺寸、内边距、边框、间隔、裁切和终端尺寸变化后的重新布局。
- 焦点管理和键盘事件分发行为明确且可预测。
- 文本输入支持光标移动、多行粘贴、历史记录扩展点；需要时支持不回显的机密输入。
- 可滚动的消息/历史视口具有稳定的选择和复制行为。
- 终端声明或提供鼠标能力时可使用鼠标；仅键盘操作也必须完整可用。
- 提供前景、背景、强调、状态、边框和低对比度辅助文字等主题/样式令牌。
- 流式文本更新限制重绘工作量，且不得不断破坏终端回滚区。
- 正常退出、取消和可恢复故障时，都要显式清理并恢复光标、输入模式、信号处理器和控制台模式。
- 提供内存渲染模式，用于确定性地检查单元格缓冲快照和布局。

## C++ 组件接口

公开 API 应保持精简且声明式，同时完整覆盖锁定参照库的目标 API；不能用“精简”作为省略公开能力的理由。可提供 PascalCase 构造接口，例如 Column、Row、Text、Border、Input、List、Viewport、Modal、Render 和 HandleEvent。并行实现开始前，合同任务会冻结每个公开类型、属性、事件和方法签名。

所有控件都接收显式状态并生成可渲染元素。控件不得直接调用 Core、模型 Provider、渠道适配器、文件系统或凭据存储。应用控制器负责将控件事件绑定到 CoreClient。

## 渲染模型

渲染器持有当前帧和下一帧的终端单元格缓冲区。每个单元格都包含字素簇/显示宽度信息和样式属性。布局完成后，只输出必要的光标、样式和文本变化，再交换缓冲区。不得把转义序列当作原始控制码混入用户文本。

文本布局必须按 Unicode 显示宽度和字素簇边界计算，不能按字节长度计算。组合符号、全角中日韩文字、无效 UTF-8 和不支持的 Emoji 序列都必须有明确的降级行为。

## 终端能力和降级

终端后端记录输入/输出句柄、VT 支持情况、尺寸、色彩深度、鼠标支持情况以及输入/输出是否重定向。应用通过 RAII 保存并恢复原始终端/控制台模式。不支持的功能应降级为文本和键盘交互，不得破坏终端状态。

Windows VT 输出需要启用相应控制台模式。输入模式决定是否能收到键盘、鼠标和尺寸变化事件。实现必须先保存再恢复原模式，不得假设系统默认值：
https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences
https://learn.microsoft.com/en-us/windows/console/console-modes

## 视觉验收

TUI 必须在 Windows Terminal 的最小支持尺寸、常用尺寸和调整后尺寸下评估。验收范围包括中文、长消息、快速流式更新、空状态/错误状态、键盘导航、启用时的剪贴板/选择操作，以及异常退出后的终端恢复。视觉合同以字符单元格为单位，不承诺文本终端不具备的像素级图形效果。
