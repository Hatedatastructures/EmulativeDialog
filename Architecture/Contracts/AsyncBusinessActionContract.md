# Async Business Action Contract V1

Status: Frozen candidate. This contract defines the Core-owned asynchronous read-only business-action registry used by Async Agent Runtime Contract V2.

## Registration and effect boundary

A business action is available to the model only when Core explicitly registers it. Every asynchronous definition contains a PascalCase action name, a canonical provider `ToolDefinition` whose name equals the registered action name, an object JSON Schema, required top-level argument fields, required capability names, a channel/conversation scope requirement, an explicit `EffectClass`, and an asynchronous handler. Existing synchronous registry handlers remain available and unchanged for V1.

`EffectClass` has `InProcessReadOnly`, `ExternalWrite`, and `ExternalIo` values and must be explicitly supplied for every async definition. Missing or unrecognized values fail closed as ineligible. R5 accepts only `EffectClass::InProcessReadOnly`: `BusinessActionRegistry::Register` rejects asynchronous definitions classified as `ExternalWrite` or `ExternalIo` before the action can be advertised or invoked. The handler is a deterministic in-process calculation over the supplied arguments and trusted context. It must not mutate persistent or cross-turn state, perform filesystem/database/network/Provider/Channel I/O, or otherwise cause an external side effect. The async invocation exposes no channel adapter, provider transport, external-write authorization token, or persistence port. Actions that need those capabilities are deferred to a separate CoreAgent `OperationRecord`/`ChannelReceipt`-backed task.

The supported action schema subset is a JSON object schema with declared top-level properties of primitive JSON types, a `required` list, and an explicit `additionalProperties` policy. Unsupported schema keywords or malformed schemas fail registration. The same schema is sent to the provider and used by Core to validate the completed arguments; required fields alone do not substitute for type or additional-property validation.

An async handler receives a Core-created `BusinessActionInvocation` containing the registered action name, provider `ToolCallId`, parsed canonical arguments, trusted Principal, trusted ConversationScope, and active AgentTurnId. It also receives the current `std::stop_token` and returns `boost::asio::awaitable<BusinessActionExecutionResult>`. Handlers return only a stable sanitized result code with status Succeeded or Failed; raw channel payloads, credentials, user message text, and provider wire objects are not receipt data. Cancellation returns a cancelled turn without manufacturing an action receipt. For a definite result, Core creates a correlated `CoreActionReceipt` per CoreAgentContract V1.1; it is not a ChannelReceipt and does not represent an external effect. R5 does not create or imply an external operation receipt or `OperationRecord` transition.

The additive registry fields are a canonical `Providers::ToolDefinition ModelTool`, an explicit `EffectClass`, and `using AsyncHandler = std::function<boost::asio::awaitable<BusinessActionExecutionResult>(const BusinessActionInvocation&, std::stop_token)>`; the existing synchronous `Handler` field remains available and unchanged for V1. The Core V2 dispatcher implements `GetToolDefinitions(const AuthorizedTurnContext&) const` and `DispatchAsync(const AuthorizedTurnContext&, const Providers::RequestId&, std::vector<Providers::FunctionCall>, std::stop_token) -> awaitable<std::vector<AsyncBusinessActionReceipt>>`.

## Eligibility and authorization

`IdentityBinding` is the trusted source for its `GrantedCapabilities`; `IdentityPolicy::Resolve` carries those grants into `ResolvedIdentity` and the Core-created `AuthorizedTurnContext`. The grant set is not read from ChannelEnvelope text, model output, or provider arguments.

The Core dispatcher builds model-visible definitions from the registry using the exact authorized context. It offers an action only when its effect class is `EffectClass::InProcessReadOnly`, its registered scope matches, and every required capability is present in the Core-resolved grant set. It never offers or invokes an `ExternalWrite` or `ExternalIo` definition. The provider cannot add or modify definitions, capabilities, Principal, scope, or turn identity.

After a correlated ToolHandoff terminal, Core validates each proposal against the registered action name and JSON object schema, verifies required fields, request and turn identity, scope and capability grants, and rejects duplicate or previously dispatched ToolCallIds. Core must not call a handler for any rejected proposal. A ToolCallId is marked before dispatch so reentrant delivery cannot execute it twice.

Each dispatched read-only handler produces one sanitized `AsyncBusinessActionReceipt` associated with the original ToolCallId, RequestId, AgentTurnId, and action name. This is the Core-created `CoreActionReceipt`; definite success, failure, rejection, or unsupported may be returned to the model as a tool-role result. The receipt never represents a platform, channel, persistence, or other external effect. A registration or dispatch attempt outside the read-only boundary fails closed before handler invocation. Unknown external outcomes and their replay/reconciliation rules belong to the separate `OperationRecord` plus definite `ChannelReceipt`-backed action task.

## Lifetime and scope

Registry, trusted context, provider lease, dispatcher, and handler dependencies remain alive until their awaited operations complete. The dispatcher does not detach work. R5 execution is limited to explicitly registered read-only in-process chat actions; external writes, persistence, channel sends, general network, Shell, host commands, arbitrary files, browser, and MCP actions are out of scope.
